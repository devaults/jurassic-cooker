# TDD-AI：AI 时代的验收驱动开发

> **本文件是"先写验收口径、再实现、再跑验收"的硬流程**。
> 验证闭环（怎么跑命令 / 怎么自证）见 [`verification-recovery.md`](./verification-recovery.md)；本文件**专注"测什么"与"先后顺序"**。

---

## 1. 核心信条

> **验收口径即测试**。AI 不擅长"自由发挥"——给 AI **可勾选的验收清单**，AI 才知道"什么算做完"。
> 严格 TDD（先写代码级 unit test）成本高、给 AI 用浪费；**验收口径先行 + 实现 + 跑验收**更匹配 AI 能力。

| 传统 TDD | AI 版 TDD（本框架） |
|---|---|
| 单元测试 | **验收口径**（acceptance criteria） |
| 红 → 绿 → 重构 | **写口径 → 实现 → 跑验收 → 修订** |
| 覆盖代码路径 | 覆盖**用户场景 + 边界 + 风险** |
| 由开发者心智驱动 | 由**用户/产品/业务**定义 |

---

## 2. 三步硬流程

### 步骤 1：写验收口径（强制先于实现）

接到任务后，**在写任何代码前**先列"做完的判据"：

```markdown
## 验收口径：<任务名>

### 功能
- [ ] <场景 1 的预期行为>
- [ ] <场景 2 的预期行为>
- [ ] <场景 3 的预期行为>

### 边界
- [ ] 空值：<空数组/空对象/null 的行为>
- [ ] 极值：<0/负数/超大/超长 的行为>
- [ ] 异常：<网络断/超时/后端 5xx 的行为>

### 性能 / 体验（如有）
- [ ] <首次加载 < Xs / 滚动流畅 / 按钮 Loading 状态>

### 安全 / 兼容（如有）
- [ ] <XSS 防住 / IE11 兼容 / 移动端可视>

### 验收命令（如可自动化）
- [ ] `npm run type-check` → 0 error
- [ ] `npm run lint` → 0 warning
- [ ] `npm run test` → 全绿
- [ ] 手测：<具体动作 + 期望结果>
```

> **必须写到文件**，不写在对话里——写进 `specs/domains/<domain>/<feature>/<stage>.md` 的"验收口径"段。

### 步骤 2：实现

按口径实现。**每完成一条勾一条**——边做边更新。

### 步骤 3：跑验收（证据）

> **跑完才能打勾**——见 [`verification-recovery.md` §1.2 完成前自证](./verification-recovery.md)

对每条验收项：
- **可自动化的** → 跑命令 + 贴输出
- **只能手测的** → 描述手测步骤 + 期望结果（最好截图或录屏）
- **未跑的** → 标"⚠️ 未验证 + 原因"

## 3. 验收口径的"好/坏"

### 3.1 好的验收口径

| 特征 | 例子 |
|---|---|
| **可观察** | "用户点击提交后，列表新增一条数据并滚动到顶部" |
| **可证伪** | "输入 `空字符串` 应提示'名称不能为空'，不应提交" |
| **场景化** | "在 3G 网络下首屏 < 5s" |
| **有边界** | "输入 1000 字以上应截断为 500 字 + 提示" |
| **可自动化** | "跑 `npm run test:e2e` 应通过用户登录场景" |

### 3.2 差的验收口径

```diff
- "功能正常"（不可证伪）
- "代码质量高"（不可观察）
- "性能好"（无指标）
- "兼容性好"（无范围）
- "用户友好"（主观）
+ "用户登录：输入正确账号密码 → 跳转首页；输入错误 → 弹 toast '密码错误'"
+ "列表为空时显示空状态占位图 + '暂无数据' 文案"
+ "并发点提交按钮 3 次只发 1 个请求"
+ "XSS：输入 `<script>alert(1)</script>` 不弹窗"
```

## 4. 与"测试金字塔"配合

> AI 版 TDD **不替代**单元测试 / E2E 测试——它定的是"该测什么"，**不规定怎么测**。

| 层 | 谁写 | 在哪 |
|---|---|---|
| **验收口径**（本文件管） | AI 起草 + 人审 | `specs/domains/<domain>/<feature>/<stage>.md` |
| **单元测试** | AI 实现时同步写（如项目已有） | `__tests__/` / `*.test.ts` |
| **E2E** | 测试工程师 / AI | `e2e/` |
| **手动验收** | 人 | 临时记录 + 截图 |

> **项目无单测框架时**，验收口径就是全部测试——别硬装单测。

---

## 5. 何时**不**用 AI 版 TDD

| 场景 | 原因 |
|---|---|
| 1-2 行的紧急修复 | 修复方式已明确，无需"先写验收" |
| 纯重构（不改行为） | 验收口径 = 原行为；写完等于没写 |
| 探索性原型 | 不知道要什么 → 先做后写 |
| 用户明确"先看看效果" | 探索模式 |

> 跳过本流程的，要在 `change-review.md §三` 交卷时**说明跳过理由**。

---

## 6. 反模式

```diff
- 不写验收口径 → 实现 → "应该可以了"（无标尺）
- 写完所有实现 → 最后补验收口径（顺序反了）
- 验收口径写"功能正常"等不可证伪的（无标尺）
- 全部勾选但实际只跑了一半（虚假通过）
- 验收口径不存档 → 写在对话里 → 上下文一丢就没了
+ 先写 → 同步勾 → 跑完才勾 → 证据存档
```

## 8. 完整工作流（示意）

```markdown
# 任务：用户列表加 role 排序

## 计划（plan-mode.md）
涉及文件、实施步骤、验证检查点...

## 验收口径（本文件）
- [ ] 列头 "role" 可点击升降序
- [ ] 排序后 URL 带 `?sort=role&order=asc|desc`
- [ ] 默认按 createdAt 降序
- [ ] 空列表有占位
- [ ] 1 万条数据排序不卡（<2s）
- [ ] npm run type-check 0 error
- [ ] npm run lint 0 warning
- [ ] 手测：点 3 次列头 → 升降升 → 数据对应

## 实施
（边做边勾）

## 跑验收
- ✅ 7 条通过（贴命令输出）
- ⚠️ 1 万条数据 < 2s 未验证（理由：缺大数据集；建议补 E2E）
```

---

## 9. 一句话总结

> **先写验收口径（写文件、不写对话）→ 实现 → 跑验收（带证据）→ 修订。**
> **"可观察 + 可证伪 + 可自动化"** 三原则缺一不可。
