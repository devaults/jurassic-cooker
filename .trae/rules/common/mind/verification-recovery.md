# Verification & Recovery：验证与排错

> 本文件是"验证"主题的唯一归属：闭环、范围、调试、错误恢复都在这里。

## 1. 验证闭环（强制）

> **核心信条：证据先于结论**。声称"完成""修好""通过"前，必须**先跑命令 + 看输出**；没跑过的不能写跑过，没验证的不能写已验证。
> 与"交卷口径"的分工：本文件管"具体怎么验证"；`change-review.md` §三 管"验证完怎么报告"。

### 1.1 四步硬流程

1. **先查命令**：查使用方项目注册表确认该项目**实际有什么脚本**——
   各项目不统一（Vue3 + Vite 常有 `type-check`，Vue2 + vue-cli 基本没有）。**禁止假设 `npm run type-check` 存在**。
2. **按实际命令跑**（范围见 §2）：有什么跑什么；都没有就跑 build + 手测，并**说明替代方式**。
3. **回归**：影响已上线功能时，跑该项目 E2E 用例，
   或按回归清单核对（见使用方本地用例清单）。
4. **失败不硬试**：不盲目重试、不用 try-catch 吞异常、不注释报错代码。

### 1.2 完成前自证（Verifying Before Completion）

> 本节是 §1 的**强约束**——所有"完成"声明前**必须**有证据。

**强制证据清单**——声称完成时**至少**附：

| 维度 | 证据形式 | 不算证据 |
|---|---|---|
| **命令执行** | 实际跑过的命令 + 退出码 + 关键输出 | "应该跑过了" / "看着没问题" |
| **验证覆盖** | 跑了什么 / 没跑什么 + 替代方式 | "已经测了"（无具体内容） |
| **已知风险** | 未覆盖的边界 / 跳过的场景 | "完全没问题" |
| **阻塞点** | 等待外部 / 未知依赖 | （隐瞒未提） |

**自检三问**——发出"完成"前**自问**：

1. 我**实际跑过**哪些命令？退出码是什么？
2. 我**没跑**的验证是什么？有没有替代方式（如手测）覆盖？
3. 有什么**我没把握**的地方需要用户确认？

**反模式**：

```diff
- "改完了" / "完成" / "OK 了"
- "应该可以了" / "看着没问题"
- "理论上会成功"
- "我修了 bug"（无复现/验证）
+ "改动完成。证据：
+   - npm run lint：✓ 0 error
+   - npm run type-check：✓ 0 error
+   - 手测：用户列表按 role 排序正常；空数据有占位
+   未覆盖：并发请求 5 个列表的竞态（需压测）；E2E 用例待补"
+ "已修复（指）某问题。证据：
+   - 复现：原代码输入 X 抛 TypeError
+   - 修复：加 ?. 防御
+   - 验证：再输 X 不抛；跑 type-check 0 error
+   残留风险：深层属性仍可能 undefined，未加全防御"
```

### 1.3 实现与验证不一致时

> **先说验证结果，再讨论原因**。

| 顺序 | 含义 |
|---|---|
| ✗ "我改了 X 看起来对，应该没问题" | 隐藏验证失败 |
| ✓ "跑命令后 Y 失败；我怀疑原因是 Z；建议改回 W 或继续调" | 事实先行 |

> 详见 [`change-review.md`](./change-review.md) §三「交卷口径」。

## 2. 验证范围与前端手测

| 改动类型 | 验证项 |
|---|---|
| 仅样式 | 格式化（有脚本才跑）+ 视觉确认 |
| 逻辑代码 | 静态检查 + 类型检查（有则跑）+ 关联测试 |
| 新增功能 | 项目全量脚本 + 手测主路径 |
| 配置/依赖变更 | 构建检查 + 全量脚本 |
| 跨模块改动 | 全量构建 + 全量脚本 + 回归清单 |

**前端专项手测**：样式/布局 → 控制台无报错 + 断点检查 ｜ 交互 → 核心路径走通 ｜
接口 → Network 状态码与响应结构 ｜ 路由 → 跳转正常 + 刷新不 404

## 3. 调试策略

`复现 → 定位范围 → 收集证据 → 分析原因 → 修复验证`。不复现不改代码，先收集触发条件。

- **样式**：查 computed style 与盒模型；优先怀疑 z-index、定位、flex/grid
- **逻辑**：断点 + Console 看变量与时序；优先怀疑异步时序、事件绑定、生命周期、闭包
- **网络**：查状态码/请求头/响应体；4xx 查参数与鉴权，5xx 找后端，请求未发出查拦截器与触发条件
- **性能**：录制长任务与布局抖动；优先怀疑大列表未虚拟化、频繁重渲染、未懒加载

### 调试禁忌

禁止"改改试试"（每次改动必须有假设）、禁止注释报错代码、禁止只改不验证、禁止一次调多个问题。

## 4. 错误恢复

**诊断优先于修复**：先收集（完整错误、发生上下文、是否可复现）→ 再分析 → 最后选方案。
**常见原因排序**：最近改动(80%) → 环境 → 外部依赖 → 原有隐藏 bug。

- 构建失败：先看第一个错误，后续多为连锁反应
- 测试失败：区分代码问题还是测试/mock 过期
- 运行异常：最小复现 → 隔离问题 → 对比验证（改动前正常吗）

### 禁止行为

禁止用 try-catch 吞异常、禁止绕过（注释掉报错代码）、禁止批量修改（一次只改一个变量，验证后再改下一个）。
工具重试次数 → [`tool-discipline.md`](./tool-discipline.md) §4

### 无法修复时

完整报告：现象 + 已尝试方案 + 可能原因 + 需要的信息/帮助；保存调试进展，不丢现场。
