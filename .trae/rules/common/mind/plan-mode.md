# Plan Mode：复杂任务的强制计划

> **本文件是"何时必须出计划 + 计划长什么样"的硬约束**，把 `self-harness.md` §一.2 的"计划先行"从软建议变成强制流程。
> 内在准则（自省 / 目标锚定 / 行为约束）见 [`self-harness.md`](./self-harness.md)，本文件不重复。

---

## 1. 何时必须进入 Plan Mode（强制）

### 1.1 触发条件（满足任一即必须）

| # | 触发 | 例子 |
|---|---|---|
| 1 | **跨 3+ 文件** | 改一个组件 + 它的 store + 它的类型定义 + 它的测试 |
| 2 | **改公共接口** | 函数签名、`props`/`emits`、导出名、API 路径、路由 `name`/`path` |
| 3 | **改数据库 / 配置 / 全局状态** | schema 变更、`config.yaml`、Pinia 大改 |
| 4 | **删除代码** | 单文件删 >30 行 / 删整个文件 / 删公共函数 |
| 5 | **跨角色协作** | 改动会"前后端契约 / 阶段交付物"产生连锁 |
| 6 | **明确不确定** | 多个技术方案需选 / 用户描述模糊 / 涉及陌生模块 |
| 7 | **改 CI / 构建 / 依赖** | `package.json` / `Dockerfile` / 升级 / 锁版本 |
| 8 | **首次接触** | 一个之前没碰过的模块 / 第一次改某个技能域 |

### 1.2 简单任务（可跳过 Plan Mode）

| 任务类型 | 例子 |
|---|---|
| 1-2 个文件 ≤ 30 行的局部修改 | 改文案 / 改样式 / 改一个函数的实现细节 |
| 调试 + 修复 | 已定位原因、修复方案明确 |
| 单测用例补充 | 在已有测试文件里加 case |
| 文档微调 | 改一段注释 / 修一个错别字 |
| 用户明确"直接做" | "不要问，直接改" |

> ⚠️ **"用户明确" 才跳过**；**自己判断"应该简单"不构成跳过理由**——认知偏差是常态。

## 2. 计划模板（强制格式）

进入 Plan Mode 后**必须**按此三段格式输出，**等用户确认才动手**：

```markdown
## 计划：<一句话标题>

### 涉及文件

- **改**：`path/to/file1.ts`（改什么、为什么）
- **改**：`path/to/file2.vue`（改什么、为什么）
- **删**：`path/to/dead.ts`（为什么能删、有无引用已查）
- **建**：`path/to/new.ts`（如需新建，列出）
- **不动但需读**：`path/to/context.ts`（改这个的依赖）

### 实施步骤（顺序）

1. **第一步**：<做什么 + 产出>
2. **第二步**：<做什么 + 产出（基于上一步的输出）>
3. **第三步**：<做什么 + 产出>
4. ...

### 验证检查点（每步对应）

- [ ] 步骤 1 完成后：<怎么验证它做对了>
- [ ] 步骤 2 完成后：<怎么验证>
- [ ] 步骤 3 完成后：<怎么验证>
- [ ] 全部完成：<端到端验证命令 + 期望输出>

### 风险与回滚（如有）

- **风险点**：<影响哪些下游/可能踩的坑>
- **回滚方案**：<git revert / 关 feature flag / 改回去要多久>
```

### 2.1 计划要"够具体"

| ✓ 好的计划 | ✗ 差的计划 |
|---|---|
| "改 `UserTable.vue`：加 `role` 列 + 排序逻辑" | "改用户列表页" |
| "步骤 1：grep 引用 `getUserList` 的 4 处 → 改函数签名 → 改 4 处调用" | "重构 getUserList" |
| "验证：跑 `npm run type-check` 期望 0 error；手测 1 个用户" | "自检通过" |

### 2.2 计划要"敢承认不知道"

- 涉及陌生代码 / 跨模块时，明确写"**先读 X / Y / Z 再回来定计划**"——分两轮做
- 不假装看懂、然后用通用经验瞎写

## 3. 等用户确认（核心）

计划写完后**必须停下来**，**等用户回复"OK"或修改意见**才动手：

> **行为准则**：
> - 用户说"OK" → 按计划执行，每完成一个步骤报一次
> - 用户说"改成 X" → 改计划，再请确认
> - 用户说"直接做" → 跳过等待，但计划**仍然要先写**（事后留档可追溯）
> - 计划里发现新问题（如某文件不能删、某函数有特殊调用）→ **回 Plan Mode 更新计划**再继续

> **反模式**：
> - ❌ 写完计划立即动手（"既然都列了，就顺手做了"）
> - ❌ 计划写得很抽象，然后"按计划"做但细节自己拍
> - ❌ 多轮中暗改计划（"刚才说改 X，实际改的是 Y"）

## 4. 实施中偏离计划 → 立即重 Plan

执行过程中若发现：
- 计划漏了文件 / 漏了步骤
- 某步骤的实际做法与计划不同
- 出现原计划没考虑的问题

**必须立刻停下来**，回到 Plan Mode：
1. 解释"原计划漏了什么 / 什么变了"
2. 给出**更新后的计划**（增删改）
3. 等用户确认后继续

> **不要**默默按新做法继续 + 在最后报告时"顺便提一下"——这是隐瞒决策。

## 6. 反例

```diff
- 用户：把 UserTable 加一列 role
- AI：（不问、不写计划、直接开始）我加好了
+ 用户：把 UserTable 加一列 role
+ AI：
+   ## 计划：UserTable 加 role 列
+   ### 涉及文件
+   - 改：src/views/User/UserTable.vue（加列定义 + 排序）
+   - 改：src/types/user.ts（如需扩 DTO，加 role 字段）
+   - 不动但需读：src/api/user.ts（确认后端已返回 role 字段）
+   ### 实施步骤
+   1. grep "user.role" 确认后端接口已包含 → 必要时先催后端
+   2. 改 DTO 类型（若需要）
+   3. 改 UserTable.vue：加列 + 排序
+   ### 验证
+   - [ ] npm run type-check 0 error
+   - [ ] npm run lint 0 warning
+   - [ ] 手测：用户列表能按 role 升降序
+   等你确认。

- 用户：改一下样式
- AI：好的，全改了
+ 用户：改一下样式
+ AI：哪个文件？改哪些元素？颜色？—— 不确定就问，不确定就 Plan
```

## 7. 一句话总结

> **复杂任务先写计划 + 等确认；执行中变了重写计划 + 再等确认。**
> **简单任务可跳过；用户说"直接做"可跳过。**
> **需要留痕 / 跨会话承接的计划落 `plans/`（Plan 通道，与 `specs/` 平级，见 [`plan-only.md`](../../../prompts/routes/plan-only.md)）；个人任务落外置个人根；一次性小改在对话内出计划即可。**
> **不要为了显得"主动"而省略计划环节。**
