# Parallel Agents：子代理并行调度

> **本文件是"什么时候该派 subagent + 怎么派 + 怎么收"的硬约束**。
> 工具使用的基础纪律（先读后改、失败重试）见 [`tool-discipline.md`](./tool-discipline.md)，本文件不重复。

---

## 1. 何时用 subagent 并行（强制判定）

### 1.1 黄金判定（三个条件都满足才并行）

| 条件 | 含义 |
|---|---|
| **① 独立** | 子任务之间**不共享状态**（不读同一文件、不改同一文件、不依赖同一中间产物） |
| **② 无顺序依赖** | 任务 A 不需要任务 B 的输出作为输入 |
| **③ 可独立验证** | 每个子任务有明确的"完成标准"（不靠别的任务结果判定成败） |

→ 三条都满足 → **强烈建议并行派发**

### 1.2 典型可并行的场景

| 场景 | 子任务拆分 |
|---|---|
| **调研** | "查 3 个项目的错误日志" / "读 5 个 SKILL.md 并总结" → 3-5 个 subagent |
| **多文件改动** | 改 A 文件 + 改 B 文件 + 改 C 文件 → 3 个 subagent（前提：互不引用） |
| **多角度分析** | "从性能 / 安全 / 可维护性三个角度评审这个函数" → 3 个 subagent |
| **跨项目对比** | "对比 A 项目与 B 项目的 X 实现" → 2 个 subagent |
| **独立测试** | 跑前端 e2e + 跑后端 e2e + 跑性能基准 → 3 个 subagent |

### 1.3 不能并行的场景（串行 or 自己做）

| 场景 | 原因 |
|---|---|
| 任务 A 的输出是任务 B 的输入 | 数据依赖 |
| 都改同一文件 | 写冲突（subagent 之间不知对方会改） |
| 都依赖同一未确认的中间产物 | 共享状态 |
| 子任务之间需要对话协商 | 串行 + 主代理调度 |
| **只是一次性 grep** | 工具调用比派 subagent 快 |

## 2. 派发模板

### 2.1 单次派发（1 subagent）

```markdown
派一个 subagent：

**任务**：<一句话说清>
**输入**：<文件路径 / 已有内容 / 上下文>
**输出格式**：<期望的产出格式>
**完成标准**：<怎么判定它做完了>
**工具限制**（如需）：<只能用 Read / 禁止 Edit / 等>
```

### 2.2 批量派发（多 subagent 并行）

```markdown
并行派 N 个 subagent：

1. **Subagent 1**：<任务> → 产出 X
2. **Subagent 2**：<任务> → 产出 Y
3. **Subagent 3**：<任务> → 产出 Z

完成后**主代理**汇总：X + Y + Z 的关键结论 + 冲突点 + 下一步建议
```

## 3. 收集与汇总（主代理职责）

### 3.1 subagent 回来后要做什么

1. **提炼关键结论**（不复读全报告）
2. **标记冲突**（subagent 之间结论矛盾 → 列出矛盾点 + 推荐解法）
3. **标记未完成**（subagent 没做到 / 跳过了什么）
4. **决定下一步**（是否需要再派 / 是否可以继续主流程）

### 3.2 主代理不要替 subagent 决定

- ❌ "Subagent A 说 X，我猜它大概意思是 Y" → 等 A 返回原文再判断
- ❌ "Subagent 跑得太慢，我自己做算了" → 接受延迟，不轻易取消
- ✓ "Subagent A 还在跑，我先处理不依赖它的部分"

## 4. 与 Plan Mode 的配合

| 阶段 | 用什么 |
|---|---|
| **计划阶段** | 在 `plan-mode.md` 的"实施步骤"里**标出哪些步骤并行** |
| **执行阶段** | 派 subagent 时**附上计划里的该步骤描述**（上下文一致） |
| **收尾阶段** | subagent 产出汇入计划的"验证检查点" |

例：

```markdown
## 计划：迁移 3 个组件到 Vue3

### 实施步骤
1. **并行**：派 3 个 subagent 分别迁移 ComponentA / ComponentB / ComponentC
2. **串行**：主代理合并 3 个结果 + 改公共依赖
3. **验证**：跑全量测试
```

## 5. 工具/资源开销

| 资源 | 注意 |
|---|---|
| **Context** | subagent 看到的上下文 ≠ 主代理的上下文；**重要信息要在派发时显式传入** |
| **时间** | 并行 ≠ 瞬时；N 个 subagent 串行派仍要 N 倍时间（要真正同时派） |
| **费用** | 多 subagent 多花 token；调研类值得，改 1 行不值得 |
| **日志/审计** | 派发的 subagent 也会写日志；如需审计，**派发前明确告知** |

## 6. 反模式

```diff
- "我先派 3 个 subagent 看看 1+1 等于几"
- （任务 A 输出还没收到）"我先假设它是 X，开始任务 B"
- "Subagent 卡了 5 分钟，我偷偷换条路绕过去"
- "派了 5 个 subagent 但只用到 1 个的输出"
- "所有改动都派 subagent 去做"（overhead > 收益）
+ 调研类 / 跨文件独立改 → 派
+ 单行修改 / 调试定位 / 强顺序 → 自己做
+ 真有顺序依赖 → 串行，subagent 只在能并行时用
```

## 7. 决策表速查

| 你的情况 | 决策 |
|---|---|
| 3 个独立调研 | ✅ 并行派 3 subagent |
| 改 1 个组件 + 1 个 store + 1 个测试 | ⚠️ 看是否互引；不互引才并行 |
| 改 A 函数被 B 引用 | ❌ 串行（先 A 后 B） |
| 跨 5 文件改一个 feature | ⚠️ 通常 1 个 subagent 做主改，1 个做验证 |
| 用户问"对比 A B C 三个方案" | ✅ 并行派 3 subagent 各查一方案 |
| 跑 build + 跑 test + 跑 lint | ✅ 并行派 3 subagent（独立命令） |
| 修复一个 bug | ❌ 自己做（subagent 无上下文） |
| 写文档（多个独立章节） | ✅ 派 N subagent 各写一节 |

## 9. 一句话总结

> **独立 + 无依赖 + 可独立验证** → 派 subagent 并行；否则**自己做**。
> **主代理** 负责派、收、汇总、决定下一步；subagent 负责**自己那一份**。
