# 阶段 1：需求分析（产品主导）

> 输入：原始需求（口语/会议纪要/用户反馈/老板要求）
> 输出：PRD v1（签字版）
> 主导角色：[产品](../../steering/product-role.md)
> 路线：被 [`full-pipeline`](../routes/full-pipeline.md) 与 [`both-ends`](../routes/both-ends.md) 引用

---

## 完整提示词模板（复制后填空）

```markdown
# 角色
你是有 5 年 B 端产品经验的产品经理，专注 [业务域，如：油气钻井 / 资产管理 / 数据治理]。
你的风格：边界清晰、不漏异常路径、对模糊需求会先问清楚再动手。

# 当前阶段
需求分析。我要把一段口语需求整理成 PRD v1。

# 输入物
## 原始需求
[粘贴需求来源：会议纪要 / 用户反馈 / 老板要求 / 工单描述 ...]

## 业务背景
[一句话说清楚要解决什么问题、为谁解决]

## 项目上下文
- 路径：<项目名（仓库名，如 oio-master-web；不写 group/ 前缀，见使用方项目注册表）>
- 阶段：[新功能 / 改 bug / 重构 / 优化]
- 是否涉及多端：[是/否，哪些端]
- 是否涉及后端：[是/否，需要哪些服务端能力]

## 已有产品参考
- 竞品：[链接或描述]
- 我司已有功能：[链接]

# 输出物
请按 PRD v1 模板产出 11 节内容，重点在第 3、4、6 节：

1. 背景与目标（why）
2. 用户与场景（who / when / where）—— 含主要用户画像与典型场景
3. 功能范围
   - in-scope（本 PRD 必做）
   - out-of-scope（本 PRD 不做，但延后可能做）
   - never-do（永远不做，明确拒绝）
4. 用户故事 —— 格式：作为 [角色]，我想要 [功能]，以便 [价值]
5. 业务流程
   - 核心路径（happy path）
   - 异常路径（至少 2 个：网络失败 / 权限不足 / 数据冲突 / 用户误操作）
   - 边界场景（空数据 / 极值 / 并发）
6. 验收清单 —— 用户视角的可验收条目，每条都能在演示时被勾选（写不出可勾选项的 = 需求没写清）
   - 格式：Given [前置] When [操作] Then [可观测结果]，或直接勾选列表
   - [ ] Given 已登录且有导出权限 When 点击"导出" Then 生成 Excel 并触发下载
   - [ ] 网络失败时导出 → 提示"导出失败，请重试"，页面不白屏
   - [ ] 空数据进入列表 → 展示空状态与引导操作，不报错
7. 非功能需求（性能/安全/兼容）—— 必须给具体数字
8. 风险与依赖 —— **后端接口可行性 / 第三方依赖 / 政策合规** 都要列出
9. [签字 + 版本号] —— 留空，由人填
10. 给 UI 的下一步指令 —— 列出 UI 必须回答的 3-5 个问题
11. **给架构师的下一步指令**（如涉及后端）—— 列出接口能力、非功能性的需求、数据量预估

# 验收口径
- [ ] 范围边界清晰：in / out-of-scope / never-do 三档都写了
- [ ] 用户故事覆盖核心路径 + 至少 2 个异常路径 + 至少 1 个边界场景
- [ ] 验收清单每条都能在演示时被勾选（不可勾选的 = 写错了）
- [ ] 非功能需求给了具体数字（不是"快"而是"< 200ms"）
- [ ] 风险与依赖列了外部依赖（后端接口 / 第三方 / 政策合规）
- [ ] 给 UI 的下一步指令至少 3 个问题
- [ ] **给架构师的下一步指令**列出关键接口能力（如需后端）

# 反例（不该做的事）
- 不要写技术方案（那是架构师的事）
- 不要画 UI 细节或选组件（那是 UI 设计的事）
- 不要替我签字
- 不要遗漏异常路径（异常路径至少等于核心路径的 1/2）
- 不要写"灵活、可配置、好用"这种不可验收的形容词
- 不要假设后端一定能改（接口可行性要在风险章节标出）
```

---

## 怎么用

1. **复制上方整段** → 替换方括号内容 → 整段发给 AI
2. **AI 输出后** → 逐项对照"验收口径"打勾
3. **不通过项** → 让 AI 修订（提示词复用，针对不通过项加一句"针对第 X 节再写一版"）
4. **通过后** → 人签字 + 给版本号 `PRD v1` → 进入阶段 2 / 3

## 常见追问（AI 输出后你需要追问的点）

| AI 输出 | 追问 |
|---|---|
| 验收清单出现"用户体验好" | "不可勾选，改成具体可观测的指标" |
| 用户故事只有 happy path | "补 2 个异常路径：导出失败 / 导出数量超限" |
| 非功能需求只写"快" | "改成具体数字：导出 1000 条 < 3s、并发 5 用户不卡顿" |
| 风险章节为空 | "列出依赖：导出后端接口 / 财务系统对接 / 数据脱敏" |
| 给 UI 的下一步指令太泛 | "改成至少 3 个具体问题：是否支持筛选条件？是否需要进度条？..." |

## 下游衔接

PRD v1 签字后，参考 [UI 设计角色卡](../../steering/ui-role.md) 第六节，把 PRD + 下一步指令发给 UI。
**若涉及后端**，同时参考 [架构师角色卡](../../steering/architect-role.md)，把 PRD 中"给架构师的下一步指令"同步给架构师走阶段 3（接口契约）。
