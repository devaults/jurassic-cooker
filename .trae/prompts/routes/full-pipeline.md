# 路线 4：完整流水线（团队协作 / 大功能）

> **场景**：从零开始的大功能，需要多人协作，完整跑 5 阶段 + QA。

## 适用判定

✅ 你拿到了：
- 原始需求（口语 / 会议纪要 / 用户反馈）

❌ 不适用：小功能 / 个人项目 → 走 [`both-ends.md`](./both-ends.md) 或 `frontend-only` / `backend-only`

## 提示词顺序（严格瀑布）

```
产品签字 ──▶ UI 签字 ──▶ 接口契约签字 ──▶ 后端 + 前端（并行）──▶ QA 签字 ──▶ 上线
   1            2              3                  4 / 5                6
```

| 顺序 | 阶段 | 主导 | 提示词 | 产物 / 签字 |
|---|---|---|---|---|
| 1 | 需求 | 产品 | [`../stages/01-requirement.md`](../stages/01-requirement.md) | `PRD v1` ✅ |
| 2 | 界面 | UI | [`../stages/02-ui.md`](../stages/02-ui.md) | `UI Spec v1` ✅ |
| 3 | **接口契约** | **架构师** | [**`../stages/03-contract.md`](../stages/03-contract.md)** | **`API 契约 v1` ✅** ⭐ |
| 4a | 后端 | 后端架构师 | [`../stages/04-dev-backend.md`](../stages/04-dev-backend.md) | 后端技术方案 + 代码 + PR |
| 4b | 前端 | 前端架构师 | [`../stages/05-dev-frontend.md`](../stages/05-dev-frontend.md) | 前端技术方案 + 代码 + PR |
| 5 | QA | QA | [`../stages/06-qa.md`](../stages/06-qa.md) | QA 结论 |

> **4a 与 4b 可并行**：接口契约 v1 一签字，前后端各自进入开发；不必等对方。
> **同步节点**：阶段 4a/4b 都完成后才能进 QA。

## 同步闸口

| 上游产物 | 未签字时禁止开始 |
|---|---|
| PRD v1 | UI、接口契约 |
| UI Spec v1 | 接口契约 |
| **API 契约 v1** | **后端开发、前端开发**（⭐ 关键同步闸口） |
| 后端 + 前端 PR 都合入 | QA |

> **个人 spec 例外**：个人 spec 落**外置个人根**（不共享），免签字，上表各闸口对其不适用。

## 关键纪律

- **每阶段必须有签字**：哪怕是个人 AI 起草 + 个人签字（**个人 spec 例外**：落外置个人根的个人 spec 免签字）
- **阶段间禁止横跳**：UI Spec 发现 PRD 写错了，必须回去改 PRD、UI Spec 重做
- **接口契约是同步闸口**：前后端对接口有歧义时，先升 v2 契约再写代码
- **QA 不替开发签字**：QA 的"通过"≠"客户对产品满意"——是"实现符合**规范**"
