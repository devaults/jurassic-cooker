# AI 思维准则（核心交付物）

> 这是整个框架的"宪法"。所有角色卡和阶段提示词都从这里派生。
> 回答两个问题：**为什么用 AI**、**怎么用 AI**。

---

## 1. 为什么用 AI —— 不是替代人，是放大角色

把每个角色拆成两类工作：

| 工作类型 | 谁干 | 典型例子 |
|---|---|---|
| **判断类**（不可让渡） | 人 | 业务取舍、跨团队协商、风险决策、价值观校准 |
| **规则类**（AI 放大点） | AI + 人审 | 信息整合、模式匹配、首版生成、规范校验、跨文档检索 |

**核心信念**：AI 干规则类、人聚焦判断类。任何把判断类丢给 AI 的用法都是越权。

**检验问句**：这一步如果 AI 错了，谁背锅？—— 答得出来的，让人干；答不出来的，多半该让 AI 干。

---

## 2. 六角色协作铁律 —— 瀑布交接 + 同步闸口

```
产品 ──► UI ──► 架构师（接口契约） ──► 后端 + 前端（可并行）──► QA
 PRD     UI Spec    API 契约          代码                   验收
                                       ⭐ 同步闸口：API 契约 v1 签字后
```

### 三条不可违反的纪律

1. **上游产物未签字，下游不开干**
   - 阶段产物必须由该阶段主导角色签字（哪怕只是"PRD v1 OK"五个字）
   - 没有签字的产物叫"草稿"，草稿进不了下一阶段
   - **同步闸口（重要）**：接口契约 v1 未签字 → 后端 + 前端均不得开工；前端仅在"接到已签字的契约"场景下可开工
   - **例外**：**个人 spec**（落外置个人根，不共享、不进团队仓）免签字，不受本条约束——仍走同一六阶段与产物，只是不阻塞自己的下游

2. **阶段内可多版，阶段间必须单版**
   - 同一阶段内可以让 AI 出 3 版、5 版对比
   - 一旦进下一阶段，所有下游只能引用**一个**明确的版本号

3. **回退只能往前，不能横跳**
   - 阶段五发现阶段一的问题，必须回到阶段一改 PRD，阶段二、阶段三、阶段四、阶段五全部重做
   - 禁止"小修一下继续走"，那是欠技术债的开始

## 3. AI 的能与不能 —— 红线清单

### ✅ AI 能干（放心用）

- 把零散信息整理成结构化清单（PRD 模板、接口清单、字段表）
- 基于已有规范生成首版代码/草图/文档
- 跨多个 `.trae/rules/*.md` 文件汇总出"本项目该遵守哪些约束"
- 对照 checklist 自检（Sonar 阈值、验收口径、命名规范）
- 把口语需求翻译成结构化 prompt
- 给多版本做差异对比

### ❌ AI 不能干（不要让它干）

- **业务判断**："这个功能该不该上"——产品决策，不是 AI 能定的
- **跨团队协商**："后端愿不愿意改接口"——人去谈
- **风险决策**："这个改动会不会引发线上事故"——基于完整上下文判断
- **价值校准**："这个文案是不是符合品牌调性"——人审
- **拍板签字**：阶段产物签字方必须是人，AI 给建议、人拍板

### ⚠️ AI 容易出错（高风险要复审）

- **数字 / 字段名 / 配置值**：会一本正经地编
- **历史 commit / 项目结构**：会用训练数据里见过的项目混淆当前项目
- **未在 `.trae/` 注册的项目**：会按通用经验瞎说
- **跨微前端的路由/通信细节**：必须人工核对 `MicroAppContainer.vue` 等关键文件

## 4. 提示词调用方式 —— 一个阶段一个完整提示词

### 4.1 不要肢解提示词

❌ 错误：分多次发"先做 X，再做 Y，最后做 Z"
   → AI 上下文会丢，每段都重新理解，浪费时间

✅ 正确：把"角色设定 + 输入物 + 输出物 + 验收口径"**一次发完**
   → 见 `../prompts/stages/` 的统一模板

### 4.2 统一结构（每个阶段的提示词都长这样）

```markdown
# 角色
你是 [产品 / UI / 接口架构师 / 后端架构师 / 前端架构师] ...

# 当前阶段
我在做 [需求分析 / 界面设计 / 前后端开发] ...

# 输入物
- 上游产物：[链接或粘贴]
- 项目上下文：[项目名（仓库名）、技术栈、相关 .trae/rules/ 文件]
- 业务背景：[一句话说清楚要解决什么问题]

# 输出物
请按以下结构产出：
1. xxx
2. xxx
...

# 验收口径
- [ ] xxx
- [ ] xxx

# 反例（不该做的事）
- 不要 xxx
- 不要 xxx
```

### 4.3 调用三步法

1. **填模板**：复制 `../prompts/stages/` 下对应阶段的提示词，把方括号换成实际内容
2. **一次发送**：整段发给 AI，不要拆
3. **逐项验收**：对照"输出物 + 验收口径"逐条打勾，不通过的让 AI 修订

## 5. 上下文锚定 —— 让 AI 用对项目

AI 默认不知道你在哪个项目、用什么技术栈。每次调用前**必须**告诉它：

### 5.1 最小上下文锚定包

```markdown
# 项目
- 路径：<项目名（仓库名，如 oio-master-web；不写 group/ 前缀）>
- 类型：Vue 3 + Vite + TS + jurassic-ui 2.x（或 Vue 2 存量 / React 等）
- 涉及业务：[一句话]

# 必须读取的规则
- .trae/rules/common/mind/self-harness.md
- 使用方本地项目规则：工作区地图（仓库关系、索引去哪查）
- 使用方本地项目规则：项目路由索引（哪个项目用哪套技能、已知坑）
- 使用方本地项目规则：该项目总览（技术栈锁定、目录/API 约定）
- .trae/rules/frontend/lang/vue.md（或 react.md）

# 必须读取的技能（按需）
- .trae/skills/frontend/crud-page/SKILL.md
- .trae/skills/frontend/api-request/SKILL.md
- ...（视任务选）
```

### 5.2 不锚定上下文的代价

- AI 会按"通用前端"经验答 → 技术栈错（Vue2 项目写出 Vue3 语法）
- AI 会引用不存在的组件/API → 代码编译失败
- AI 会忽略 Sonar/质量规范 → 写完就被打回
- AI 会混淆同名项目（同一名称在不同仓库/版本间可能对应不同技术栈）

## 6. 交付物冻结线 —— 阶段间的"签收墙"

### 6.1 每个阶段必须有 3 件东西

| 交付物 | 谁产 | 谁签 | 冻结条件 |
|---|---|---|---|
| **产物正文** | AI 起草 + 人修 | 主导角色 | 验收口径全打勾 |
| **变更摘要** | AI 起草 | 主导角色 | 一段话说清楚"做了什么/影响哪些文件" |
| **下一步指令** | 主导角色写 | 下游角色 | "给 UI：请基于本 PRD 做 ..." |

### 6.2 冻结的最小仪式

哪怕非正式，至少满足：

```markdown
PRD v1 ✅ 已签字 @产品名 2026-09-27
- 范围：xxx
- 不做：xxx
- 风险：xxx
```

没有这三行，下游默认"这是草稿，我要再问一遍"。（**个人 spec 例外**：落外置个人根、不共享，免此仪式。）

## 附录：常见反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 让 AI 直接出最终代码 | 跳过了需求/界面思考 | 走完六阶段，每阶段都有人审 |
| 把多个阶段塞进一个提示词 | AI 没法聚焦，输出泛泛 | 一个阶段一个提示词 |
| 让 AI 替人"拍板" | 责任无法追溯 | AI 给选项，人选并签字 |
| 不告诉 AI 项目上下文 | 输出用错技术栈 | 每次都带"最小上下文锚定包" |
| 阶段产物没签字就传 | 下游不知道这是不是终版 | 必须有"签字 + 版本号" |
