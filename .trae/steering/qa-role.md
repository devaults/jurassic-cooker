# 角色卡：QA 工程师

> 主导阶段：**QA 验收（阶段 6）**。负责把前后端实现对照上游所有产物（PRD / UI Spec / API 契约 / 技术方案）逐项验证，给"通过 / 有条件通过 / 不通过"结论。

---

## 一、这个角色是谁

QA 工程师的核心不是"找 bug 凑数"，而是：

1. **功能契约验收** —— 对照 PRD §6 验收清单逐条勾选（产品口径）
2. **设计走查** —— 对照 UI Spec §8 走查 checklist（视觉 / 交互 / 可访问性 / 边界）
3. **接口契约实测** —— 前端实调用 + 后端实现 与 `API 契约 v1` 字段 / 错误码 100% 对齐
4. **前后端实现验收** —— 跑 `qa/checklist.md` 的 E（前端）/ F（后端）两节
5. **给最终结论** —— 通过 / 有条件通过 / 不通过；遗留项必须明示

AI 在 QA 阶段是**对照清单助手 + 模板生成器**：把验收点生成表格、把前后端自检项整理成统一 checklist、把走查步骤转成可勾选任务。

---

## 二、AI 放大点（这个角色最该让 AI 干的事）

| 任务 | 为什么适合 AI | 典型提示词信号 |
|---|---|---|
| 上游产物 → 验收 checklist | 模板化 | "基于 PRD §6 + UI Spec §8 + API 契约 v1 + 两个技术方案，生成 qa/checklist.md" |
| 后端实现 vs API 契约对比 | 跨模式检索 | "对照 `design-contract.md` 扫 controller，列字段不一致处" |
| 前端实现 vs UI Spec 组件清单 | 模式匹配 | "对照 UI Spec §4 组件清单扫页面，列出私换组件 / 缺组件 / 多组件" |
| E2E 用例生成 | 模板化 | "基于 PRD 用户故事与业务流程，生成 Playwright 用例脚本" |
| 异常路径枚举 | 跨场景枚举 | "针对 `POST /api/v1/<resource>` 枚举至少 5 个异常路径测试点" |
| 自检项核对 | 跨规则匹配 | "对照 `change-review.md §二` 拉自检清单" |
| 跨模块影响分析 | 跨文件检索 | "列出 [功能/任务] 改动影响的所有模块" |
| 写测试报告 | 结构化输出 | "把本轮验收结果写成测试报告（含覆盖率 / 通过率 / 遗留项）" |

---

## 三、判断红线（AI 不能干的部分）

| 判断 | 为什么必须人 |
|---|---|
| **"通过 / 不通过"最终结论** | 责任归属；QA 是上线前最后一道闸 |
| **性能指标是否达标**（响应时间、QPS） | 需实测环境与负载，不能纸面估算 |
| **业务规则对错**（业务口径） | 需业务方确认；AI 不能理解业务边界 |
| **跨端体验评估**（视觉一致性 / 交互流畅度） | 需真实用户视角，AI 易漏主观体验 |
| **线上风险评估**（数据库变更 / 接口变更 / 配置变更） | 影响范围与回滚策略需全局视角 |
| **遗留项"可以上线"判定** | 责任归属；不能让 AI 决定哪些风险可以等 |

## 四、阶段产物清单

```markdown
QA 结论 - [功能名]
├─ 0. 元信息（上游版本号 + 状态）
│   └─ 0.1 运行环境（URL / 登录方式 / 登录后入口；跑前端用例必填，**凭据不入库**）
├─ 1. 验收对照
│   ├─ A. 需求验收（PRD §6）
│   ├─ B. 设计走查（UI Spec §8）：视觉 / 交互 / 可访问性 / 边界
│   ├─ C. 接口契约验收（design-contract.md v1）：字段 / 错误码 / 鉴权
│   ├─ D. 非功能需求（PRD §7）：性能 / 安全 / 兼容
│   ├─ E. 前端实现（tier: frontend）：仅当有前端改动时跑
│   └─ F. 后端实现（tier: backend）：仅当有后端改动时跑
├─ 2. 测试覆盖（单元 / 集成 / E2E / 手测）
├─ 3. 走查结论：关键路径 + 截图 / 录屏位置（产物默认落 cooker `.screenshots/`，可 local 覆盖）
├─ 4. 已知问题 / 遗留 / 上线风险
├─ 5. 结论：通过 / 有条件通过 / 不通过
└─ 6. 签字（QA + 后端架构师 + 前端架构师 + 业务方）
```

> **签字规则**：哪一节全部收口签字，需哪几个角色签。
> - 仅前端：QA + 前端架构师
> - 仅后端：QA + 后端架构师
> - 前后端都改：QA + 后端架构师 + 前端架构师
> - 仅改契约：QA + 接口架构师

## 五、调用 AI 的最小提示词模板

> 完整模板见 [`../prompts/stages/06-qa.md`](../prompts/stages/06-qa.md)。

骨架：

```markdown
# 角色
你是有经验的 QA 工程师，熟悉 [前端 Vue 3 + Vite + TS / 后端 Java + Spring Boot] 的端到端验证。
你的职责：对照上游各阶段产物逐项验证，给"通过 / 有条件通过 / 不通过"的结论。

# 当前阶段
QA 验收。我要把 [功能名] 的所有交付物走完一遍，给最终结论。

# 输入物
- PRD v1：[链接]
- UI Spec v1：[链接]
- API 契约 v1：[链接]
- 前端技术方案 v1：[链接]
- 后端技术方案 v1：[链接]

# 必须读取
- 使用方本地的 E2E 用例清单（如有）
- skills/frontend/quality-review/SKILL.md
- skills/frontend/sonar/SKILL.md
- skills/frontend/playwright-e2e/SKILL.md（要跑 / 新增 E2E 用例时）

# 输出物
按 qa/README.md + checklist.md 模板产出。

# 反例
- 不要只看静态代码不跑测试
- 不要放过"小问题"——任何未勾项都要写在遗留里
- 不要替开发签字
- 不要在没有环境/数据的情况下写"通过"
```

## 六、与下游的衔接

QA 通过后，进上线；不通过则回流到对应阶段：

```markdown
执行 checklist：
- [ ] 从 main 拉新分支（如需 release notes）
- [ ] 上线前确认所有 T-NN 卡片已勾
- [ ] 上线前确认所有自检项已勾
- [ ] 上线后回写"上线结论"到 qa/README.md
- [ ] 线上事故 / 反馈入知识库 `work/qa/`
- [ ] 30 天内复盘遗留项

## 回流路径

| QA 不通过 | 回流到 |
|---|---|
| 需求验收不通过 | 阶段 1 产品（PRD 修订） |
| 设计走查不通过 | 阶段 2 UI（UI Spec 修订） |
| 接口契约不通过 | 阶段 3 架构师（API 契约升 v2） |
| 前端自检不通过 | 阶段 5 前端（前端任务回流） |
| 后端自检不通过 | 阶段 4 后端（后端任务回流） |
| 性能 / 安全不达标 | 阶段 4 / 5（视瓶颈） |
```
